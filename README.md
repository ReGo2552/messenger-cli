# TCP CLI Messenger

Сейчас клиент и сервер обмениваются строковым эхом. Бинарный кодек реализован в [internal/protocol](internal/protocol/codec.go). Подключение кодека к чату запланировано на [второй этап](PROJECT_PLAN.md).

## Проверки

- `make test` запускает тесты всех пакетов.
- `make check` запускает `go vet ./...` и тесты с детектором гонок. Эту же проверку выполняет `make` без аргументов.

## Протокол v1

Каждый кадр начинается с шестибайтового заголовка. Сразу за ним идут ровно столько байт, сколько указано в поле длины.

| Смещение в байтах | Поле | Значение |
| --- | --- | --- |
| 0 | Версия | `0x01` |
| 1 | Тип | Однобайтовый код из таблицы ниже |
| 2–5 | Длина тела | `uint32`, Big Endian, от 0 до 65 536 байт включительно |

Тело сообщений чата содержит JSON в UTF-8. Кодек передаёт тело как байты. Разбор JSON относится к обработчику сообщения.

| Код | Тип | Направление | Пример тела |
| --- | --- | --- | --- |
| `0x01` | `TypeHello` | Клиент → сервер, первый кадр задаёт ник | `{"nick":"alice"}` |
| `0x02` | `TypeMessage` | Клиент → сервер | `{"text":"Привет"}` |
| `0x02` | `TypeMessage` | Сервер → клиент, сервер подставляет ник отправителя | `{"from":"alice","text":"Привет"}` |
| `0x05` | `TypeError` | Сервер → клиент | `{"message":"Ник уже занят"}` |

При чтении кодек отклоняет неизвестную версию и превышение лимита сразу после заголовка. Конец потока между кадрами даёт `io.EOF`, обрыв внутри кадра даёт `io.ErrUnexpectedEOF`. При записи нулевое поле `Packet.Version` выбирает текущую версию.
